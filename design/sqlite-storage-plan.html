SQLite 存储层重设计 — 调研报告与实施计划

以插件私有的 node:sqlite 数据库作为唯一派生存储：会话级 / 步骤级行式建模，版本不符即全量重建，查询由 Drizzle ORM（schema-as-code + typed SQL）承载。现有插件投影注册、JSON 缓存、内存聚合与粗粒度路由全部打破重做；折叠引擎、dsh 自有 title/metadata 投影读取与全部 dsh 原生数据接缝保留。

依据：dsh master (39163dd, 0.2.2-rc.3) 与 dsh-context 0.85.1 源码逐行调研；所有论断附文件:行号证据。2026-11-17 修订版。

2026-11-17 修订摘要（基于对 dsh 0.2.2-rc.3 / dsh-context 0.85.1 的复核）
  • 数据正确性：打开门禁改为「先读后写」，拒绝 application_id=0 且有表/未知表的库；file_ops 增加 ordinal 修复多文件搜索主键冲突；last_seq 默认 -1；log_mtime 改 REAL 并增加 log_revision。
  • 口径：新增 §5.15「family × inherited × root」矩阵；seed_cut_seq 统一继承过滤；family_root 统一家族聚合，普通 fork 不并入；turn/steps 明确根自身口径。
  • 时间旅行/API：严格 seq<X；timeline 返回 system/header/live/floors；sessions 返回 turns/steps/created_day 与 self/family 两套值；events 同时富化前驱/后继；tool-calls 改为排序相关 keyset。
  • 数据访问层：新增 §3.4/§5.0.1：drizzle-orm@1.0.0-rc.5 + node:sqlite 同步驱动；schema-as-code；DDL 由 schema 生成并后处理 STRICT/WITHOUT ROWID；查询用 typed builders，递归 CTE/window 用插值 table/column 的 sql 模板；不使用 drizzle migration。
  • 启动/首屏：新增 §8.0：apply 只做打开/门禁/DDL/路由注册（p99 ≤10ms），hydration 延迟到首屏后；首屏 serve-first 读 SQLite 不 await 扫描；冷读改「交互 > 列表 > 回填 > 清理」优先级池（2–4 并发）；统一 WorkScheduler + 按资源分执行器，回填/Reaper 只在空闲预算内运行，quick_check 后台 worker。
  • 一致性/恢复：增量续折改从 fold_state.last_seq 起；新增 clean_shutdown 双向尾部校验；folding 状态与分片崩溃清理；Reaper + session_tombstones 清理已消失会话（防复活）；多进程 destructive refold 用 CAS。
  • 性能/内存：两把排序键由折叠器维护绝对值；活会话工作态设内存 LRU 上限；tally 加 limit；索引补齐 family_root/cur_total/model/running/provider/duration。
  • 兼容/文字：保留 sessionProjections/sessionProjectionCache 读取 dsh 自有 title/metadata；更新 node:sqlite 稳定性表述与 0.85.1 基线；明确 days 的 all 窗口、search_text 非 ASCII 搜索、preview 截断与 unsupported 重试。

2.3 折叠引擎产出的全部数据形态（新表设计的直接输入）

事件 → 派生事实（每条都应成为一行）

  • assistant/message → LLM 调用行：当时上下文构成（system/tools/user/inject/skill/assistant/tool/total）、usage 四桶、turn/step、TTFT 与 gen 时窗。
  • step/start→step/end → 步骤行：wall/active/wait/idle/tool-busy、首 token 时刻、节拍封顶标记（fold.ts:585-655）。
  • tool/call→tool/result 及 PTC 对 → 工具调用行：名称、起止、时长、错误、shell 命令文本（≤4096）、退出码、程序名归组（fold.ts:400-575）。
  • 表面节点（user/inject/skill/assistant/tool）→ 表面行：类别、tokens、reasoning/answer/call 拆分、imgs、工具名、预览；compaction/prune/system 替换 → gone_seq 归档标记（fold.ts:169-289）。
  • compaction/prune/inject/model/mode → 事件行（fold.ts:683-970）。
  • request/header → 头纪元行 + 逐工具 schema 估值行（headers.ts:65-108）。
  • system/message → 系统提示行（被替换的旧提示从状态删除，fold.ts:369-385）。
  • file ops（read/write/search）→ 文件操作行（fold.ts:743-801；shared/fileOps.ts）。
  • 技能装载三条路径（invocation / result / PTC dispatch）→ 技能装载行（activity.ts:199-321）。
  • 计时 span（ttft/reasoning/text/toolarg/tools/other）→ span 行（fold.ts:618-640）。

折叠态维护的标量（终稿口径，评审修订）

  • 回写 sessions 的仅两把排序键：billed_tokens / cur_total（由折叠器维护绝对值、随 flush 写入；全量重折/回填时按行集校验）+ 最新态 model / provider / reasoningEffort / contextWindow / maxOutputTokens / last_user + family_root / seed_cut_seq / created_day / search_text 等不可变派生键。
  • 运行计数（turns/steps/injects/…）与计时总量（wall/ttft/gen/…）折叠器不再驻留 —— 全部由子表派生（§5.2 派生对照）。

不入库（服务时计算 / 直读 dsh）

  • 成本 = usage 行 × 价目表（host 已持有，1h TTL）；faces/misses 由 DISTINCT(provider,model) 现算。
  • running / archived / 分组 = workspaceRegistry / agents 镜像列（带刷新触发）。
  • 标题 = dsh title 投影；消息正文、工具输出、fleet 消息 = 按需 RPC 读原始日志。

3.2 核心决策

编号决策理由与代价
D1SQLite 为唯一派生存储同时取代插件的投影注册与 session_projcache 插件行（dsh 自有 title/sessionListMetadata 投影仍读取）、overview JSON 缓存、请求期内存 feed、detail/delta/facts 冷缓存。消除「同一派生数据存 4 处」的根本冗余；查询/聚合/分页成为索引扫描而非 JS 遍历。
代价：折叠器必须自行管理活会话折叠与冷回填（两者皆有已验证的实现模式可复用）。
D2折叠引擎保留为纯计算，改造成「行发射器」applyTimeline/applyActivity 的计量口径（token 估值、峰谷分桶、idle 刻雕、TTFT 锚点）经过 diff-fold 差分校准，全部保留；改变的是终点——状态不再攒成大对象，而是在终结点(步骤结束/工具结算/请求落定)发射为行。lifetime totals/timing 不再在折叠器中累积，由 steps/requests/timing_spans 行派生；单步/单请求的计量公式不变，但 step/end 与 assistant/message 的同一段代码要改为「算完即发射」，不是简单外包一层。

④ 版本与重建策略

4.1 数据库身份与版本门禁

-- 打开序列：先读后写（与 dsh session-query-sqlite 的拒绝顺序一致）
1. DatabaseSync(path)                     -- 目录 0700、新文件 0600（dsh 同款）
2. 读取 PRAGMA application_id / PRAGMA user_version / sqlite_master 用户表清单
3. 门禁（失败即 close + 拒绝打开，绝不写入/删除）：
   - application_id 非 0 且 ≠ 0x44534358('DSCX')  -> 他方数据库，拒绝
   - application_id = 0 且存在用户表               -> 非空且无法证明归属，拒绝
   - application_id = DSCX 且 user_version ≠ STORAGE_VERSION -> 视为本插件旧/新版本：DROP 全部用户表 -> 重建
   - application_id = DSCX 且 user_version = STORAGE_VERSION 且有未知表 -> 拒绝（同版本出现未知表，可能是损坏/他方写入）
   - application_id = 0 且无用户表                  -> 新建
4. 门禁通过后才应用有副作用的 PRAGMA：
   PRAGMA journal_mode = WAL;
   PRAGMA foreign_keys = ON;
   PRAGMA busy_timeout = 5000;
   PRAGMA synchronous  = NORMAL;          -- 派生可重建数据，WAL+NORMAL 足够
   PRAGMA cache_size   = -8000;           -- 8 MB 页缓存上限
5. 门禁通过后先写 PRAGMA application_id = 0x44534358（'DSCX'，区别于 dsh 的 'DSHQ'），
   再建 schema，最后写 PRAGMA user_version = STORAGE_VERSION；版本戳只在布局完整后落盘
   -- crash 中途留下 app_id=DSCX + user_version=0/旧值 + 部分已知表 → 下次按版本不符重建，
   -- 不会落入 application_id=0 且有表 → 永久拒绝的死局
场景动作
application_id 非 0 且 ≠ 'DSCX'拒绝打开（他方数据库，永不触碰）——同 dsh session-query-sqlite/schema.ts:58-63。不写 application_id、不改 journal_mode。
application_id=0 但已有用户表拒绝打开（无法证明是本插件库；可能是被误放到该路径的普通 SQLite 库）——同 dsh session-query-sqlite/schema.ts:64-67 的“非空且非公认派生索引”拒绝。
application_id=DSCX 且有未知用户表user_version ≠ STORAGE_VERSION：视为本插件不同版本，DROP 全部用户表重建（满足需求 2，数据可再生）。user_version = STORAGE_VERSION：同版本出现未知表 → 拒绝（不 DROP 未知表），记录日志供诊断。
user_version ≠ STORAGE_VERSION（仅限 DSCX 库）DROP 全部用户表（含未知表）→ 重置 user_version=0 → 重建 schema → 重播种 meta。app_id 已证明是本插件库；不同版本的表结构都是派生数据，重建安全（需求 2）。reset 细节：按子表→父表顺序 DROP，或临时 PRAGMA foreign_keys=OFF（需在事务外），重建后恢复 ON。大库启动约束：旧库行数大时不要在 P0 主线程 DROP 大表——close 后把旧文件改名为 index.sqlite.rebuild-<ts>、立即新建空库，旧文件/旧行后台清理；P0 保持 ≤10ms。先例：session-query-sqlite/schema.ts:68-101 resetDerivedSchema。
空库（application_id=0 且无表）先写 application_id（DSCX）→ 建 schema → 最后写 user_version；中途 crash 走「DSCX + 版本不符/表缺失」重建路径。
拒绝打开后的服务形态路由统一 ready:false / startup_phase=degraded，不写库、不改库、不退 :memory:（避免把「路径上有非本插件库」误当成可用空库）；记录日志与修复提示，dsh 会话列表不受影响。
application_id=DSCX、user_version=STORAGE_VERSION 但表缺失/不完整视为半建库：DROP 已知表 → 重建 schema → 重播种 meta；不保留可能不一致的旧行。
quick_check 失败 / 打开异常P2 后台 worker 每次启动执行 PRAGMA quick_check（低优先级；clean_shutdown=0 或打开异常时提高优先级），不在 apply 主线程执行；失败则 close、把文件改名为 index.sqlite.corrupt-<ts>（不直接 rm，避免误删他方文件），再建新库；失败 → :memory: 降级（全功能、随进程消失）+ warn；两者皆败 → 路由统一 ready:false。
建库/重建 DDL 来源schema.generated.ts 的 CREATE_SCHEMA_SQL（Drizzle schema.ts 生成后追加 STRICT, WITHOUT ROWID）；不执行 drizzle migration、不建迁移表；application_id/user_version/PRAGMA 由打开序列负责。见 §5.0.1。
检测到旧 overview-cache.v1.json首次成功建库后删除（一次性清理，失败静默）。
磁盘与多进程：数据库目录沿用 dsh 的 0700、文件 0600（session-query-sqlite/schema.ts:37-41）；WAL 的 -wal/-shm 同目录。重建/改名只在确认文件未被另一进程持有时执行；否则退 :memory: 并告警。

4.2 STORAGE_VERSION 的 bump 规则

  • 任何表结构 / 字段语义 / 统计口径变化都必须 bump —— 因为不迁移：旧行口径与新查询混杂即是数据错误（符合编码标准「数据准确性第一」）。包括：seed_cut_seq/family_root 的判定规则、search_text 的折叠方式、day/period/program 的折叠算法、preview 截断规则、家族/继承过滤矩阵的任何变化。
  • 派生数据完全可重建，bump 的代价仅是首次启动的回填时长（有节流与 worker，不阻塞使用；未回填会话按 §8 的 coverage 显示 «—»）。
  • 与 fold_state 的状态载荷格式变化共用同一版本号：载荷不兼容时该表整体清空（等价于回退到全量重折叠）。
  • meta.db_epoch（或等价的随机种子）在重建时更新：会话级 unchanged 同时比较 db_epoch + detail_rev + pricing_version，因此旧库 token 不会在新库误命中。

  • day = 折叠时用 dayKeyOf() 算好的本地日键（'YYYY-MM-DD'）——日聚合一律走它，SQL 内不做时区运算。
  • family_root = 家族根会话 id（仅 origin='subagent' 的会话参与家族，普通 fork 不参与）；seed_cut_seq = session/end-seed(inherited=true) 的事件 seq，NULL=无继承种子；search_text = 折叠后的小写标题/cwd/last_user 拼接（只用于搜索，不展示）。
  • 布尔 INTEGER 0/1；枚举 TEXT + CHECK；金额永不入库。
  • 避让 SQL 关键字：模型变更用 model_from/model_to（不用 from/to）；file_ops 的单事件多行用 ordinal（0..n-1）区分，timing_spans 用折叠器分配的 span_seq。

冗余判定五规则（需求 4/8）

  1. 原文不复制：消息正文、工具输出、system prompt 文本、fleet 消息不入库；展示需要处只留 ≤2,000 字符 preview 并置 preview_truncated（渲染必需的截断预览，全文按需走 RPC，§5.6）。
  2. 折叠态只落排序键：sessions 仅保留 billed_tokens / cur_total 两把排序与热路径键（折叠器维护绝对值，随 flush 写入；全量重折/回填时按行集校验），其余计数/计时一律子表 GROUP BY 现算 —— 禁止为查询新造预聚合（days/tallies 全废，会话级计数列亦裁剪），并消灭「计数器 = 子表 SUM」的双源不变量。
  3. 可由行集 GROUP BY 现算的 → 不设列：当前构成分类拆分（surface_nodes 求和）、成本（usage×价目）、名目统计、文件聚合、turns/steps 全部现算；仅保留排序键（billed_tokens、cur_total）与列表显示所需最小列。
  4. dsh 服务在请求时零成本可得的 → 镜像列 + 明确刷新触发：archived/workspace_title/running/title/blank（刷新触发见 §8.5），字段语义以 dsh 为准。
  5. 派生但查询高频且纯函数的 → 折叠/扫描时算好存列：day、period（峰/谷）、starts_turn、program、plugin 归属、family_root、seed_cut_seq、created_day、log_revision、search_text——存一次，省去查询端 JS 重算。

5.0.1 Drizzle schema 与生成 DDL（选定实现）

Schema 是表/列名的唯一来源

  • src/host/db/schema.ts 为 15 张表各定义一个 sqliteTable；列用 text/integer/real + notNull/default/$type；复合主键用 primaryKey({columns})，索引用 index/uniqueIndex（部分索引用 .where(sql`...`)），约束用 check/foreignKey。schema 同时导出 TABLES（由 table 对象派生），打开门禁的 allowlist 与重建 DROP 列表从这里取，不维护第二份表名清单。
  • 查询行类型从 typeof table.$inferSelect 推导，写入类型从 $inferInsert 推导；禁止在 query 模块手写表名/列名字符串。
  • 枚举列用 text('...', { enum: [...] }) 得到 TS 联合，CHECK 由 check() 同步定义；状态常量只在 schema/常量模块出现一次。

DDL 生成与校验

  • drizzle-kit export --sql --dialect=sqlite --schema=src/host/db/schema.ts（dev-only）从 schema 直接输出建表/索引 SQL（不写 migration/snapshot）；scripts/db-schema.mjs 为每个 CREATE TABLE 追加 STRICT, WITHOUT ROWID，生成 schema.generated.ts（CREATE_SCHEMA_SQL）。15 张表都有主键，单键表（meta/fold_state/session_tombstones）同样适用；「单键除外」只指主键列数，不是行存例外。
  • 运行时 import CREATE_SCHEMA_SQL 并 db.$client.exec() + 打开序列 PRAGMA；不调用 migrate()，不创建 __drizzle_migrations。
  • CI 跑 scripts/db-schema.mjs --check 重新生成并 diff；M1 parity 测试应用 SQL 到内存库，比对 PRAGMA table_list(strict/wr)、table_info、index_list/index_info、foreign_key_list，任何漂移失败。
  • Drizzle RC5 不能表达 STRICT/WITHOUT ROWID，所以后处理脚本是必需的、受测试的构建步骤；若生成器无法稳定输出某个结构，M1 停下来修生成器，不允许手写第二份 DDL。
为什么不直接用 drizzle-kit migration：本设计的版本策略是 user_version 不符即全量重建，迁移链没有语义；把 schema 当 DDL 生成源、把生成 SQL 当运行时建库脚本，既保留 schema-as-code 的类型安全，又避免 migration 状态机与重建逻辑双轨。

⑧ 回填与及时刷新机制（主动回填 / 写通）

8.0 启动、首屏与交互优先级（评审修订：不阻塞 dsh 启动）

结论：原稿把 listSessions 对账、尾部校验、stat 巡检与逐会话回填写进 apply() 的 boot 序列；即使内部 await，也会把 dsh 启动与首个会话列表交互拖进插件的数据管线。SQLite 是同步 API，coldReads 现状是串行 FIFO，fold pool 是单 worker/单 pending——都不满足「主动、异步、并发、池化、交互优先」。本节是硬约束，§8.1 的重活只能发生在 P2/P4。
阶段做什么硬预算 / 约束
P0 apply 快路径（同步）解析路径；DatabaseSync 打开；读取 application_id/user_version/用户表；门禁；小库 DDL / 大库改名换新库（§4.1）；注册路由；clean_shutdown=0；返回。p99 ≤10ms（不含首次冷磁盘 I/O）；禁止 listSessions / stat / quick_check / 标题投影读取 / 回填 / 全表 COUNT；不等待任何日志读取或网络。安全阀：若首次 open/DDL 仍超预算，先注册路由、把 open/DDL 放 setImmediate，query 返回 starting，绝不在 apply 里 await。
P1 首屏query/* 直接读当前 SQLite 行（镜像列/已回填行）；pending/folding/unsupported 返回 «—» 与 coverage；不 await 扫描；后台调度 reconcile。首个 query/sessions p95 ≤50ms（含冷页缓存）；首屏不得等待 listSessions/stat/标题刷新；dsh 会话列表完全独立（插件不再注册投影，apply 不阻塞它）。
P2 延迟 hydration在「首个路由响应后 + 安静窗（建议 1.5–2s）」或「无 UI 时 5s」启动：listSessions 对账、标题/blank 刷新、尾部校验、stat 巡检、回填队列。只在交互空闲时占用主线程；有交互请求时暂停/让路；可被 dispose/abort 取消；不在 apply/inject 同步前缀里做。
P3 主动回填按 updated_at 降序的活跃优先队列；>30k 事件用 worker 行批次；节流 8s 工作/2s 暂停。只使用「剩余预算」；主线程 slice ≤8ms、写事务 ≤2k 行或 ≤5ms；事件循环最大阻塞 ≤16ms；交互队列非空时不得启动新 slice。
P4 维护/清理Reaper（§8.7）：已消失会话候选、墓碑、分片删除、TTL 清理。最低 lane；30–60s 周期；连续交互最多延后 30s；删除走 SqliteWriter；不在首屏/apply 中运行。

优先级与池化

  • 交互 > 列表 > 回填 > 清理：coldReads.admit(read, {lane})；交互（detail/context/timeline/tool-calls/file-ops）优先，列表（sessions/summary/days/tally）次之，回填再次，Reaper 清理最低。禁止现状的 tail.then 串行 FIFO，也禁止回填/清理占用交互 lane。
  • 池：冷读/折叠并发 2–4（默认 2，可配）；主线程同时只允许 1 个写事务；worker 池 1–2 个（>30k 会话）；heap gate 仍保留，在入池前检查。
  • 让路：回填在每个 slice/事务边界检查 interactivePending/lastInteractiveAt；有交互在途或最近 500ms 内有交互 → 不启动新 slice；正在执行的 slice 不能抢占，但用 ≤8ms 预算保证尽快结束。
  • 启动静默窗：P2 在首个路由响应后延迟 1.5–2s；无 UI 时 5s；持续交互时最多再等 10s，之后以低优先级、≤8ms slice 缓慢推进，不为等待静默无限延迟 hydration。首屏为空/新库时仍先返回空 + coverage，不等待回填。
  • 状态可见：query/status 暴露 startup_phase(open|hydrating|ready|degraded)、hydrating、integrity_check、coverage；UI 用占位而非阻塞等待。

SQLite 同步 API 的硬约束

  • DatabaseSync 的每次 exec/事务都在主线程；Drizzle node-sqlite 是同步 API，db.transaction({ behavior: 'immediate' }) 回调禁止 await；回填禁止大事务直接跑：拆为 ≤2k 行/事务，事务间 setTimeout(0) 让路。所有写入（活写通/回填/重建/meta）统一走 SqliteWriter 单写者队列；worker 只做折叠/重聚合并返回行批次，不直接写 DB，避免多写者/跨线程连接问题。
  • quick_check 不在 apply 执行：P2 每次启动都在后台 worker 执行（低优先级；unclean 或打开异常时提高优先级）；期间插件数据标记 integrity_check=true/ready:false（或只读现有行并显式标注），不阻塞 dsh 会话列表。
  • 版本不符重建：小库在 P0 做 DROP/建表；大库 close 后改名为 index.sqlite.rebuild-<ts>、立即新建空库（P0 只做 rename+DDL），旧文件后台删除；标记 rebuilding/ready:false，dsh 会话列表不受影响。
验收口径：dsh 启动到会话列表可交互的时间相对无插件基线不回归（插件 apply 热盘 p99 ≤10ms；冷盘首次 open 若超 10ms 则走「先注册路由、setImmediate 开库」安全阀）；首屏 plugin query p95 ≤50ms；回填期间事件循环最大延迟 ≤16ms；10k 会话/脏库/空库/崩溃四种启动场景均满足；50 并发 subagent 下交互 lane 不被回填饿死。

统一调度器与资源共享（评审修订）

现状的 coldReads 已经由 fleet/attachment/detail/delta/facts/commands/heads/backfill 共用（src/host/index.ts:41-74），但它只是 tail.then 串行 FIFO。正确做法不是给每个消费者再造一个池，而是把这个共用 admission 点升级成共享调度器：策略（优先级、预算、堆门、去重、取消、指标）共用，底层执行器按资源类型分开。

资源类执行器 / 并发共享方式不能共享的边界
Async I/O（日志 open/read、stat、listSessions）AsyncIoExecutor；4–8 并发，加权 lane所有消费者走 scheduler.admit({resource:'io', lane, key, signal})；同 key 的 in-flight 去重；取消沿 AbortSignal 传播。stat 与 read 各有独立并发上限，避免 stat 风暴挤占 detail；slow network 不进入此池。

  • 共享逻辑：一个 WorkScheduler 提供 admit(task, {lane, resource, key, budget, signal})、优先级、in-flight 去重、堆门、取消、超时与指标；消费者只描述任务，不再各自实现 tail.then 或独立 semaphore。
  • 共用资源：AsyncIoExecutor、MainThreadSlicer、WorkerExecutor、SqliteWriter 是共享实例；backfill、detail、overview、stat、title 刷新、live seed/refold、Reaper 全部提交到同一 scheduler，但按 resource 落到不同执行器。
  • 饥饿与公平：交互 lane 优先；P3 回填在交互静默后恢复，不为 P3 在连续交互中强行插入 slice；P2 的轻量 hydration（listSessions/stat/tail check）在持续交互 10s 后以 ≤2ms 低频推进，不抢占 P3。长时间无交互时按 8s/2s 节奏推进；队列深度/等待时间/服务时间进 query/status，hydration 可延后但不会丢任务。
  • 去重：同一 session 的 cold read/fold 在 detail 与 backfill 同时请求时共享同一 promise；同一 stat path、同一 overview query key 同理，避免重复日志读取和重复折叠。
  • 死锁约束：任何任务不得在持有 worker/写事务时等待主线程 lane；SqliteWriter 不得在事务内等待 AsyncIo。违反时 scheduler 记录错误并放弃该任务，而不是让宿主饿死。

8.7 会话清理（Reaper）：删除已消失会话的全部派生内容

已考虑删除，但原稿只有「差集两轮删除」，没有独立的清理任务、墓碑和并发池。本修订补一个低优先级 Reaper：它是 P4 维护 lane（P2 hydration 之后），复用 §8.0 的 WorkScheduler，不是 dsh 启动路径的一部分。

项规则
触发P2 hydration 完成后启动；作为独立的 P4 维护 lane，每 30–60s 运行一次（不跟随 §8.4 的 5s 请求扫描窗）。连续交互时最多延后 30s，之后以 ≤2ms 低频推进候选发现；首屏期间不启动。它不是新线程：listSessions/stat/persistence 是主进程服务，不能搬到通用 worker；删除必须走 SqliteWriter 单写者。候选发现/stat 走 AsyncIoExecutor（stat 用独立 16 上限，不占日志 read 槽）。
候选判定同时满足：① listSessions() 成功（空列表合法）；② id 在 sessions 表但不在 listed 集合；③ sessions.get(id) 不存在（非 live）；④ fold_status 不是 folding/deleting；⑤ 持久化/stat 可用（不可用则 Reaper 禁用，纯 live 模式绝不批量删冷行）；⑥ stat(id)=undefined；⑦ log_path 文件不存在，或 log_path 为 NULL 且连续缺席 ≥24h；⑧ 连续两轮 Reaper 缺席 + ≥60s 宽限；⑨ folded_at 早于 60s。任一不满足都不删；stat 返回 undefined 但文件存在（malformed/空 header）视为损坏，不删。
防复活删除前先写 session_tombstones(id, deleted_at, reason)（reason 只能是 'missing-from-list'|'log-file-missing'），取消/拒绝该 id 的 queued/in-flight backfill、seed、refold（候选已排除 live，不取消 live 写通）；清掉内存工作态。**写事务查墓碑的范围**：backfill/seed/refold/scan INSERT/UPDATE 查；墓碑写入、删除事务、TTL 清理自身豁免。墓碑保留 7 天（可配），过期前若 sessions 行仍在则续期重试。会话重新出现时由扫描窗先删墓碑、重置 fold_status='pending'、last_seq=-1 再重新准入。
删除事务先置 fold_status='deleting'（查询隐藏），再按子表/主键 ≤2k 行或 ≤5ms 分片删除（Drizzle db.delete(table).where(...)），最后删 sessions 行；小行集可单事务。FK CASCADE 仅作为最终兜底，不作为唯一分片机制。失败保留墓碑与 sessions 行，下轮从 deleting 重试；崩溃不会留下「部分子行 + fold_status=ok」。
关联修复删除父会话后，受影响的整个子树重算 family_root 到最近的存活非 subagent 祖先；若没有存活祖先，则子树中直接子会话各自成为根。保留仍存在的子会话，并 bump 受影响行的 detail_rev/generation，避免 overview 丢失完整范围。
可观测query/status 增加 reaper{running,last_run_at,candidates,deleted_sessions,deleted_child_rows,failed,tombstones}；日志只记录 id 与原因，不打印会话内容。
为什么不是「独立线程」：dsh 的 sessionQuery/sessionPersistence 由宿主主进程组合（dsh: packages/session-query/session-query/src/index.ts:186-190、packages/session/session-persistence/src/index.ts:51-68），worker 无法直接调用这些服务；node:sqlite 的 DatabaseSync 也不能跨线程共享。把清理放进独立线程会引入第二个写者、连接归属和跨线程服务代理，反而破坏单写者与 WAL 预算。正确的「异步、并发、池化」是：Reaper 作为后台任务 + 候选发现走 AsyncIo 池 + 删除走单写者队列；CPU 重的清理计算（如大行集分片计划）可交给共享 WorkerExecutor。

10.3 明确的限制（诚实声明）

  • Drizzle RC：drizzle-orm/node-sqlite 目前只在 1.0 RC；stable 0.45.4 不可用。exact pin 是兼容性的一部分，不代表 Drizzle 1.0 已稳定。
  • Drizzle schema 表达不了 STRICT/WITHOUT ROWID：DDL 由 schema 生成后追加表选项；这是受测试的构建步骤，不是手写第二份 DDL。若生成器/后处理失败，M1 必须停下。
  • 复杂 SQL 的边界：递归 CTE、window、PRAGMA 仍用 sql 模板，只有插值的 table/column 有保护；裸 SQL 片段必须限制在 db/queries 并加 EXPLAIN/fixture 测试。
  • 聚合数值：Drizzle SQLite 的 sum() 返回字符串；计数/整数聚合 cast integer，金额/比率/浮点用 mapWith(Number)/sql<number>，不能整数截断。
  • 不使用 drizzle migration：migration API/迁移表被禁用；版本重建仍以 user_version 全量重建为准。
  • 不做全文检索：消息正文检索应由 dsh sessionQuery FTS（部署可选启用）承担；本库仅 title/cwd/last_user 的 search_text LIKE（小写折叠覆盖非 ASCII；last_user 仍只保留 200 字，超出部分的搜索命中是已知边界）。
  • 身份窗口：日志被原地重写且保持 path+size+mtime 的情形不可见（与现状 overviewCache 相同的窗口，非新引入）；stat().revision 可用时优先。
  • 镜像列陈旧 ≤5s（title/blank/running/archived）：与现状请求期直读持平；若未来 harness 推送这些变化可进一步收紧。
  • 首屏可能不完整：P1 直接读已回填行；pending/folding/unsupported 显示 «—»，hydration 在首屏后自动补齐。这是「不阻塞 dsh 启动/首个会话列表」的有意取舍，不要求用户额外操作；coverage 可见。
  • quick_check 延迟：P2 每次启动在后台 worker 执行（unclean/打开异常提高优先级），插件数据在检查完成前按 ready/partial 状态展示；dsh 会话列表不受影响。若检查失败则重建/降级（§4.1）。
  • Reaper 的保守边界：持久化/stat 不可用时禁用删除（纯 live 模式绝不批量删冷行）；log_path 为 NULL（跨进程未 materialize 的 pending 会话）需连续缺席 ≥24h 才进入候选；stat 返回 undefined 但日志文件存在（malformed/空 header）不删。宁可留下不可达行，也不误删仍存在的会话。
  • 崩溃后的尾部校验：P2 始终校验所有 last_seq≥0 的会话（read(sessions.last_seq,1)）；clean_shutdown 只影响优先级/并发，不跳过正确性。若宿主日志缓冲丢失且文件身份未变，插件无法从身份识别，只能依赖尾部 read 校验；干净关机也接受 WAL/NORMAL 的最后一次提交回滚语义。
  • 多进程写者为会话级 last-wins；destructive refold 用 last_seq/revision CAS 防止旧写覆盖新写，但不提供跨进程合并/事务语义。
  • preview 截断：surface preview ≤2,000 字符并标注 preview_truncated；上下文浏览器/RequestDetail 在节点展开时自动按 seq 走 history RPC 取全文，不要求额外手动加载；未接入的视图会显示截断文本。
  • 路由契约破坏性变更：旧 14 条路由中 6 条删除、6 条保持不变、2 条改造（delta/fleet），客户端同仓同发，属插件内闭环（无第三方消费面）；版本按 breaking 处理（下一个 minor，如 0.86.0 + compatibility.md 全面更新）。
