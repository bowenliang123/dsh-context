# 数据交互与前后端要求

- 客户端
	- 尽可能减少首次加载、长会话加载、复杂会话、多 agent 团队等的卡顿，必须实测充分证明
    - 数据准确性，一致性和完整性必须保证，不能出现数据缺失、错误、重复等问题
      - 比如，提供的会话统计，按条件过滤后的分类统计等，不得出现浅缓存、局部等问题
	- 按需加载，永远加载当前功能和状态在所需最小的内容，按功能、按板块、按 id、按最小化需要获取
      - 比如，上下文浏览器默认未展开前可以不加载里面的内容，展开后再加载
	- 异步加载
    - 分页加载，永远加载当前所在列表中所需最小的内容
      - 比如，上下文浏览器中某些部分的内容可以按分页加载，避免一次性加载过多内容
	- 所有位点采取采取滑动窗口，不得出现内存泄露，并降低常驻内存
	- 自动加载更多，不得出现用户需要额外手动加载更多
	- 及时释放数据和元素，充分降低内存占用
	- 减少或避免前端数据计算，尽可能使用后端提供的数据和接口能力
	- 减少或避免前端的缓存，例如内存、LocalStorage 等，后端如果有的，及时拉取就行
	- 如果确实必要的缓存，注意管理为稳定的 key、必须有 ttl、上限控制等
	- 前端元素在等待元素的时候，也要尽量按最终样式来占位展示，减少加载后视觉上的冲击
		- 比如板块、卡片的高度等的视觉冲击
	- 用户功能连续性（无感加载更多或回收等）、数据的数据最终一致性（最终展示的统计信息等）是必须保证的
	- 不得出现内存泄露，不得出现随着时间、随着会话变多而常驻和峰值内存变多的问题

- 后端
	- 数据的数据最终一致性是必须保证的
    - 所有调查和决定必须结合 dsh 源码现场的证据作为依据，不能凭空想象和假设
	- 彻底拆分和提供细粒度、不同用途、不同场景的API，高内聚、低耦合
    - 全局统筹、彻底设计细粒度的 model，尽量避免重复
	- 减少内存占用和冲击，必须实测收益，包括峰值内存和常驻内存
	- 尽可能把数据来源后端化
		- 比如 npm 版本检测、models.dev价目、会话金额耗费等
	- 尽可能把数据计算后端化
		- 比如 会话金额耗费、会话聚合等
	- 尽可能预先聚合所需展示的内容
	- 尽可能异步计算
    - 尽可能并发、高效计算
	- 及时通知前端信息的变化，重新拉取或推送，采取合适的策略
    - 永远采取效率最高的实现方式，减少扫描数据的范围，避免不必要的字段、计算和数据传输
    - 不得出现内存泄露，不得出现随着时间、随着会话变多而常驻和峰值内存变多的问题
    - 尽可能提前主动计算，降低对用户卡顿的影响，并充分提升前台用户体验
      - 比如: dsh启动后，在本插件内主动启动异步线程，来聚合上下文洞察里所需的聚合信息，来主动回填活跃和最近使用的会话信息等
